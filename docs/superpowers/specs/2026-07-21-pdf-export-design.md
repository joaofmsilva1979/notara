# Printable PDF Export — Design Spec

## Context

- Existing pipeline (`guitar_tab_pipeline`) renders tabs as plain ASCII `.txt` via `pipeline/tab_render.py`'s `render_tab`/`write_tab`.
- The original Mac/iOS app design (`docs/superpowers/specs/2026-07-17-mac-ios-tab-app-design.md`, Feature 2) specified a native PDFKit/Core Text rendering inside a future SwiftUI app: portrait, Courier New, 7-8pt, paginated by bar groups, one PDF per voice when multi-guitar mode is active.
- No Mac app exists yet — only the Python CLI pipeline. Decision (this session): implement the PDF export as a new Python pipeline stage now, consistent with how every other feature so far (tuning detection, chord-detection accuracy) has been built directly into the CLI, rather than waiting for a not-yet-started native app.
- Explicitly rejected in the original design, for the same reason it's rejected here: HTML→PDF conversion (e.g. via weasyprint), because an intermediate layout engine risks subtly misaligning the monospace ASCII tab columns. `reportlab`'s Canvas API is used instead for direct, point-level text placement — the closest Python equivalent to native Core Text control.

## Goal

Add a `--export-pdf` CLI option that produces a paginated, portrait, Courier-font PDF rendering of the tab already generated by `tab_render.py` — readable and print-ready, without reimplementing any note/chord placement logic.

**Explicitly out of scope for this chantier:** chord diagram legends (requires fretboard-diagram rendering logic that doesn't exist yet — a separate, later chantier if wanted).

## Key constraint discovered during design: line width vs. page width

`tab_render.render_tab`'s default `bars_per_line=4` produces lines of roughly 197 characters (`1` string-label char + 4 × (`CELL_WIDTH=3` × `COLUMNS_PER_BAR=16` + 1 separator `|` = 49 chars/bar)). Courier's character width is a fixed 0.6× the font's point size (standard PDF font metric). At 8pt, that's 4.8pt/char; at 7pt, 4.2pt/char. An A4 page (595.28pt wide) with 36pt margins on each side leaves ~523pt of printable width — enough for only **~109 characters at 8pt, or ~124 at 7pt**. 197 characters does not fit at either size.

**Resolution:** the PDF export must call `render_tab(..., bars_per_line=2)` specifically for PDF output (independent of whatever `bars_per_line` the `.txt` export uses) — this produces ~99-character lines, which fits comfortably within both the 7pt and 8pt budgets. `bars_per_line=3` (~148 chars) does not fit either size and is not used.

## Architecture

### New module: `pipeline/pdf_export.py`

```python
def export_pdf(path: Path, bars: List[ChordSegment], notes: List[FrettedNote],
                key_estimate: KeyEstimate, tempo: float, source_name: str,
                tuning: Tuning, font_size: int = 8) -> None:
```

Steps:
1. Call `tab_render.render_tab(bars, notes, key_estimate, tempo, source_name, tuning, bars_per_line=2)` to get the ASCII tab text (this is the ONLY place that generates the actual note/chord layout — `pdf_export.py` never re-derives it).
2. Split the text into lines; skip the first 8 lines (the existing header comment block: 7 `#`-prefixed lines + 1 blank line — see `tab_render.render_tab`'s current output) to get to the body.
3. Group the remaining body lines into blocks of exactly 8 lines each (1 chord-label row + 6 string rows + 1 blank separator row) — this is `render_tab`'s per-line-group output shape at any `bars_per_line`.
4. Compute, from `font_size`, how many whole 8-line blocks fit on one page (see Pagination below), and lay out pages accordingly, never splitting a block across two pages.
5. Draw a page header on every page — title (`source_name`), key (`key_estimate`), tempo, tuning name, and page number — formatted directly from the typed parameters already passed into `export_pdf` (not re-parsed from the rendered text).
6. Save the PDF to `path` using `reportlab.pdfgen.canvas.Canvas`.

### Pagination math

- Page: A4 portrait (595.28 x 841.89 pt), margins 36pt on all sides.
- Character width: `0.6 * font_size` pt (Courier's fixed metric).
- Line height: `font_size * 1.15` pt (single-spaced monospace convention).
- Header block reserves 5 line-heights at the top of every page (title + key/tempo/tuning line + blank + page number, with one spare line of breathing room).
- Printable body height per page = `841.89 - 2*36 - 5*line_height`.
- `lines_per_page = floor(printable_body_height / line_height)`
- `blocks_per_page = lines_per_page // 8` (integer division — partial blocks are never placed; if this rounds to 0 at some font size, that's a configuration error the CLI should reject up front, not silently mishandle — see Error Handling)

### CLI (`main.py`)

- New flag `--export-pdf` (boolean, `action="store_true"`, same style as the existing `--export-midi`).
- New flag `--pdf-font-size` (`type=int`, `choices=[7, 8]`, `default=8`).
- Output path: `<output_path_stem>.pdf` next to the `.txt` output (mirroring the existing `--export-midi` → `<output_path_stem>.mid` pattern).
- If `--voices 2` is also active, produce one PDF per voice (`_guitare_aigue.pdf`, `_guitare_grave.pdf`) using the same `export_pdf` function with each voice's own notes/label text, mirroring how `--voices 2` already produces two `.txt` files today.
- `--export-pdf` and `--pdf-font-size` are independent of `--export-midi`; both can be combined.

## Error Handling

- If `blocks_per_page` computes to 0 for a given `font_size` (i.e., even one block doesn't fit within the page + margins), raise a clear `ValueError` from `export_pdf` before attempting to render anything — this should not happen for the supported font sizes (7, 8) on A4 with the specified margins, but the function must fail loudly rather than produce a broken/empty PDF if the math is ever wrong (e.g., after a future margin/size change).

## Testing

`pdf_export.py`'s PAGINATION MATH is pure and testable without ever invoking `reportlab`'s actual PDF drawing (which would require rendering-level/visual verification, out of scope for unit tests):
- A function `_blocks_per_page(font_size: int) -> int` isolates the arithmetic described above; unit-testable directly (e.g. assert `_blocks_per_page(8)` and `_blocks_per_page(7)` both return a positive integer, and that 7pt fits at least as many blocks per page as 8pt since characters/lines are smaller).
- A function `_split_into_blocks(body_lines: List[str]) -> List[List[str]]` groups body lines into 8-line chunks; unit-testable with synthetic line lists (e.g. 16 fake lines → 2 blocks of 8; a non-multiple-of-8 input is a bug in `render_tab`'s output shape, not something this function needs to handle defensively — see Known Limitations).
- The actual PDF byte generation (`export_pdf` itself, using `reportlab.pdfgen.canvas.Canvas`) is integration-level and not unit-tested, consistent with existing precedent (`separation.py`, `transcription.py` have no unit tests either, for the same reason: the meaningful verification is "does the output look right," not something a fast unit test can check). Verified instead via an optional manual smoke test that opens/inspects the generated PDF's page count and first page's text extraction.

## Known Limitations (to document in the module docstring)

- Assumes `render_tab`'s body output is always a multiple of 8 lines (chord row + 6 string rows + 1 blank separator, repeated) at any `bars_per_line` — true for the current `tab_render.py` implementation, but if that module's line-group shape ever changes, `pdf_export.py`'s block-splitting would need updating too.
- No chord diagram legend (out of scope, see Goal).
- Font size is limited to 7 or 8pt by CLI `choices` — matches the explicit design requirement ("taille 7 ou 8 ou 9"); 9pt was requested but the line-width math above shows 9pt (5.4pt/char) allows only ~96 characters at 523pt printable width, which is tighter than `bars_per_line=2`'s ~99 characters — i.e., 9pt would NOT reliably fit even 2 bars per line. 9pt is therefore not offered as a choice; only 7 and 8pt are guaranteed to fit.
- Page margins (36pt) and page size (A4) are hardcoded constants, not CLI-configurable, consistent with keeping this chantier scoped.
